# Changelog

All notable changes to the plugins in this marketplace. Each plugin is versioned on its own, in its `plugin.json`, and released as a `{plugin}--v{version}` tag.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and each plugin follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- `kc-conventions` 2.1.3 and `kc-gates` 3.2.6: an expensive check whose result later work throws away runs once, on the finished work. The working agreement gains "Order of work on a task": assess and present the cause and fix, get approval, build with lint, types and the affected tests only, open a draft pull request, run the one review-and-QA pass, then mark it ready, and only then look back over every correction, review comment and QA finding of the task and write its lessons as one batch (the session-start reminder and "Keep the instructions current" now say the same, instead of a lesson per piece of feedback as it lands). `kc-ready-for-review`'s "Not before" and `kc-code-review`'s self-review trigger now also rule out a review fan-out or an app walk on uncommitted work shown to the person for approval, since the hand-off pass repeats both. It catches a full review run before the code stops changing, screenshots for a pull request taken before the copy is final, and a performance profile taken halfway through the refactor it judges. It comes from a small two-file fix that was reviewed by every gate and walked in the app while uncommitted, then reviewed and walked again at hand-off: four review rounds and two app walks, about two-thirds of the task's time.
- `kc-conventions` 2.1.2 and `kc-gates` 3.2.5: a change's tests cover what it adds, once, at the unit that owns it. Testing §T1 asked for a test of every new behaviour but said nothing against more, and §T3's "both ways" asked for a case on every side of every condition, so a small change could come with tests that restate unchanged behaviour, re-test a shared unit through each caller and add a case per guard, until the test diff dwarfed the code diff. §T1 (rule, box, detail) now fails a case that pins behaviour the diff didn't change, re-tests a shared unit through a caller, or repeats the owner's case; the caller tests only its own wiring. §T3 names two sides that need no new case: the off side of an opt-in the change adds, and a guard that only keeps an absent optional input from crashing; the verification gate accepts either as a survivor verdict. §T4 fails a helper or fixture only one test uses and a nested `describe` with no setup of its own. It catches a shared formatter's new option re-tested through every page that passes it, a table's new sortable columns tested again in the list page that turns them on, and an endpoint's new filter tested again in each client. It comes from a shared component's new opt-in option whose tests grew to twelve cases across two files, three levels of nested `describe` and about four times the code change, re-testing old behaviour; four flat cases covered it.
- `kc-gates` 3.2.4: every comment of one review goes up as one review. `kc-post-review` posted a review with no top-level body one request per comment, to the single-comment endpoint, because GitHub's docs list `body` as required for a `COMMENT` review; that endpoint wraps each comment in a review of its own, so two comments showed on the PR as two reviews. A test post showed GitHub accepts a `COMMENT` review with inline comments and no body. `build-comment-payloads.sh` now gathers the checked comments into one `review.json` (with `--body-file` adding a body when there is one) and prints one command; the skill's posting shapes, protocol, pre-draft checklist (a new box) and audit (a new line) follow. The habit behind it: when an API offers a batch and a one-at-a-time endpoint, check what each leaves behind for the reader before choosing, and test a documented limit before working around it. It catches a code review sent as comments that each notify the author, a ticket's subtasks created one call at a time so each sends its own email, and calendar invites sent per attendee instead of as one event.

- `kc-verify` 2.2.1: QA runs the change, including someone else's. `kc-ui`'s rule against stand-ins listed stories, fixture pages and test harnesses, but not reading the code or looking at the author's screenshots, so a QA pass on a teammate's change could be reported from those, with running it offered as an option. The rule now names both as stand-ins, says the change runs with its own code (every branch it needs, a server change included, on throwaway data when it migrates), and that running it is never offered as a choice; the matching gate box counts no state the app wasn't put in. It catches an empty state judged from the component's code, an error message judged from a validation rule without submitting the bad value, and a layout judged from a screenshot taken at one width. It comes from a design QA of a pull request reported from its code and its author's screenshots; running it showed an error toast with a raw field name and a value wrapping mid-word, which neither showed.
- `kc-gates` 3.2.3: a review opens the designs its linked issue links before judging what a person sees. `kc-code-review`'s §G3 read the issue's text but not the prototype or mockup it pointed to, so a review could fault copy, layout or visibility the design itself specifies. §G3 now has the design walked in each state the diff changes, drops a finding the design contradicts, and makes a question of one where the issue's text and the design disagree, citing both. The verification gate's §V7 wants the designs named with the states walked. It catches a review calling an empty-state message wrong that the mockup has word for word, one asking to move a panel the design places there, and one flagging a sample shown on a help page that the prototype shows, where the real question is that the issue's technical notes say otherwise. It comes from a review that marked a settings page's copy and a card's layout as wrong without opening the prototype its issue linked; the prototype had both.
- `kc-gates` 3.2.2: `kc-post-review` loads for any message the user sends under their own name, not only PR comments: its trigger now names chat messages, DMs and ticket comments. Its voice box also says what matching the user's past messages means: their casing, length, punctuation, how they place links and the words they use, so a draft tidier than those messages fails. It catches a chat DM drafted as clean sentences for someone who writes lowercase one-liners, a ticket comment with headings from someone who writes two plain lines, and a reply that spells out what the user would leave to a link. It comes from a chat request for approvals, drafted after reading the user's DMs with that person but written in polished prose, which the user did not send.
- `kc-gates` 3.2.1: every claim a review comment or report line makes about the code is checked at the head SHA, including claims the reviewer's own wording adds. `kc-code-review`'s "a gate finding is a lead" rule already checked the cited line, but not a claim sharpened while rewording a gate's finding for the report, and `kc-post-review` checked suggested changes for new bugs but not what a draft says the code does. Its pre-draft checklist gains a box and its audit a column (the `file:line` read for each claim). It catches a comment saying a record is loaded twice when the load is cached and only the formatting runs twice, one saying a query runs per row when the rows are preloaded, and one saying a button is hidden when it is only disabled. It comes from a drafted comment that said a file was parsed twice, reworded from a finding that said a helper ran twice; the parse was cached.
- `kc-conventions` 2.1.1: a write-up of findings for other people is short. The working agreement's "short and to the point" rule now covers write-ups of findings, and a new line under it says what one holds: what was found, the few numbers that decide it and how they were measured, and the options, in a handful of bullets, with the method, queries, caveats and dead ends left in your notes unless someone asks. It catches an investigation written into a ticket as a section per data source and query, an incident summary that walks every log search, and a spike's outcome that retells each approach tried. It comes from an investigation write-up with sections for method, queries and ruled-out causes that its readers would not have read; the version cut to findings, counts and options was the one that went out.
- `kc-gates` 3.2.0, `kc-conventions` 2.1.0, `kc-verify` 2.2.0, `kc-instructions` 3.2.0, `kc-autopilot` 0.3.0, `kc-usage-band` 2.1.0, `kc-image-preview` 2.1.0: the kit's plugins stay current during a session, and a session says when it runs an older one than is installed, so nobody has to remember to update or reload. Claude Code updates plugins once, minutes after a session's first message, and a session keeps what it loaded until the person types `/reload-plugins`; a change merged after that, from another session, GitHub or auto-merge, reached a long session only if someone remembered both. A background `UserPromptSubmit` hook in kc-gates (`scripts/update-marketplace.sh`) looks at most every ten minutes and, when the branch the marketplace's clone follows has moved, runs `claude plugin marketplace update` and `claude plugin update` for each user-scope plugin installed from it. It follows Claude Code's switches: `autoUpdate` from a settings file's `extraKnownMarketplaces` entry, then `known_marketplaces.json`; nothing while `DISABLE_UPDATES`, `DISABLE_AUTOUPDATER` or `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` is set, unless `FORCE_AUTOUPDATE_PLUGINS=1`. A failure is told to Claude once and retried on the next look. Every plugin in the kit gains a `UserPromptSubmit` hook (`scripts/check-loaded-version.sh`, one file linked into each) that compares the version its hooks run from with the ones `installed_plugins.json` records, and tells Claude once per session and version when it is behind, so Claude asks for `/reload-plugins` before a review pass works on rules the session never loaded. It comes from a review pass that ran on the previous version of its own rules because the fix to them merged 14 minutes after that session's one update.
- `kc-gates` 3.1.7: `kc-ready-for-review`'s round 2 confirms instead of discovering. Two passes left 19 and 24 findings after round 2. Traced line by line, most sat on code the author wrote while fixing round 1, which no gate had seen; none sat on lines a gate wrote that the author applied as written; the rest were constructs round 1 sampled instead of listing (an untested branch, a flaky test, a bare number, a shell name the sweeps couldn't parse). 3.1.4's rule, that the author walks their own fixes against every checklist, made the author the detector of their own mistakes and didn't move the count. Now the gates write each fix as exact edits (a new optional input of `kc-code-review`, so a review on request and `kc-post-review` keep one-line findings), the author applies them as written and runs the checks, and one fix check runs before round 2: `kc-code-review`'s phase-1 gates on round 1's fixes with the whole diff beside them, plus the hand-off checklist and QA where the fixes reach. A finding that changes the shape of the change is settled first and restarts round 1 once. Every review in the pass reads the local head, and nothing is pushed before round 2. The report counts what the fix check found beside round 2 and gives each open finding its origin (a fix line, missed by round 1, pre-existing); those findings are sorted like a reviewer's comments, toward at most two after round 2 and none 🟠. The caller runs `kc-conventions`' new mutation sweep on each review's whole diff, once per area, and the testing gate grades its output. Gates write nothing in the checkout under review, its git index included, and run nothing that takes a fixed shared resource (an end-to-end suite's port, a shared build folder, a dev database); they name the end-to-end spec and the orchestrator runs it. After round 1's review, its findings become a short list of the kinds of mistake the PR makes (step 5): one agent searches the rest of the diff for each kind, every edit is checked against the list before it lands, and the fix check and round 2 get the list as `kc-code-review`'s new lessons input. A replay of one pass found that most of round 2's findings were kinds round 1 had already flagged on other lines. A round-2 finding that reverses a call made earlier in the pass, or two gates pulling one construct opposite ways, is now a disagreement the user settles once (step 9), and the answer is written to the repo's `.claude/review-conventions.md`, which the review creates when a repo has none (`kc-code-review`, a contested call is never settled by the agent); every topic gate reads that file before grading and raises nothing it settles. A second replay showed most of round 2's remaining findings were such reversals. Requires `kc-conventions` 2.0.5.
- `kc-conventions` 2.0.5: three things a gate used to sample are now listed by scripts, and correctness gains §B16. `kc-testing/scripts/surviving-mutants.sh` is the mutation sweep behind testing §T3. In a throwaway `git worktree` of HEAD, so the working tree is never edited even when the run is killed, it runs the tests a set number of times (one failure means flaky or broken, and no mutant runs), then breaks each condition and early exit on the diff's added code lines one at a time, never inside quotes, and prints each break no test noticed: an untested branch, or code that changes nothing. Each run gets a deadline from the slowest baseline run, a mutant that no longer parses is skipped as unviable, and every line its time budget didn't reach is listed. The review's caller runs it and the testing gate grades its output. Outside shell and Python it also drops each plain operand of `&&` and `||`, forces a ternary to each branch, and weakens a regex literal (`^` or `$` removed, `\w` widened to `.`); `as-casts.sh` lists casts to object and tuple types too. Correctness §B16 adds "written by two writers at once" to the states, simplicity §P1 greps the repo for a literal the diff moves into a shared constant, and testing §T4 leaves a repeated one-expression read inline (simplicity §P11). Clarity §C16 gets `numeric-literals.sh`, listing bare numbers other than 0 and 1 (comments, a declaration that names its number and an exact expected value skipped). The naming sweeps now read shell scripts: assignments, `local`s, functions and loop variables for §N5, snake_case functions without a leading verb for §N6. The testing sweeps share one test-path pattern, `KC_TEST_PATHS`, which also covers `_spec.rb`, `spec/`, `tests/` and `e2e/`. Correctness §B16: a value written now and read later (a cookie, a cache entry, a URL parameter, a file, a row, a flag) is read in every state it can reach by then (missing, stale, written by an older version, someone else's, half-written), shown as a table of states and events with the line that handles each. It catches a page reading an address from history after the order it names was refunded, a sign-in hint cookie that outlives its session, a draft saved by an older version, and a retried job whose first run half-finished. Has a gate box.
- `kc-gates` 3.1.6 and `kc-conventions` 2.0.4: a review's suggestions must not introduce bugs. A suggested change is code the author writes because the reviewer asked, so it gets the bug check our own change would. New correctness §B15: a change to a condition, fallback, default or validation moves only the states it is for. List every state that reaches the line (saved and unsaved values, empty ones, each option of a choice, records saved under an old rule) with the result before and after; any other state whose result moves is a new bug. `kc-code-review`'s rule for proposed fixes is widened from "passes every checklist" to "passes every checklist and breaks nothing", with that walk required for any fix that changes behaviour, in code or in words. The verification gate's §V8 fails a behaviour-changing rewrite with no state table, and `kc-post-review` gains a pre-draft box and an audit column for it. Other cases it catches: `||` changed to `??` that lets `NaN` through, an early return for a missing value that also skips `0`, a stricter validation that blocks every later edit of records saved before it. It comes from a review suggestion that narrowed a label's fallback to the saved option it was meant for, so the unsaved choice of that same option lost its label. Has a gate box.
- `kc-gates` 3.1.5 and `kc-conventions` 2.0.3: writing goes to engineers, not an audience. It says the point accurately and stops, with no stage-setting, no recap of what is already done and no design explained back to the reader, while staying grounded and humble rather than curt. Existing rules are widened rather than joined by a new one: `kc-post-review`'s plain-words tone rule (now with a before/after example), its politeness rules reworded and merged to "grounded and humble" so they no longer ask for soft framing, and the working agreement's "short and to the point" rule, which now covers chat answers, issue replies, PR descriptions and commit messages. It comes from review drafts that opened by listing what the author had already fixed and explained each ask at length; the short, plain rewrite was what a person would have written.
- `kc-gates` 3.1.4: `kc-ready-for-review`'s round 1 holds its own fixes to every gate, so round 2 comes back close to clean. A fix checked only against the rule that raised it brings new findings into round 2 (a rename whose name no longer says what the value holds, a label added under a new key when an existing key already holds that text, a test that asserts on a class name, a description rewritten for the hand-off checklist that now names something it must not). Step 4 now has the author walk every line the fixes changed against every gate's checklist, the hand-off checklist and the QA rules before committing them, and put two gates' conflicting fixes for one construct to the user in round 1 instead of picking one; step 8 walks the fixes the user picks the same way, and the report's round-1 cell records the walk and what was asked. It points at `kc-code-review`'s existing rules for proposed fixes rather than adding a second one. It comes from a pass whose round 2 raised 12 items, 7 of them inside round 1's own fixes.
- `kc-verify` 2.1.0: `kc-ui` is split in two. `kc-ui` keeps how a change looks: the design's state matrix, loading, empty, error and overflowing states, sibling measurements, viewports, themes and font scale, the visual defect scan and layout tracing, plus the setup (real data, dev-only sign-in), the report and the walkthrough video. The new `kc-ux` checks a person can use it: the walk as someone new to the product, familiar flows (simplicity §P17), pointers to other screens, tenant switching, writes showing up elsewhere, old, archived and cross-tenant records, doing things twice, empty and invalid saves, Discard, confirmation and alert wording, signed-in state, a fresh record end to end and the keyboard pass. It reuses kc-ui's setup, evidence rules and report. No check was dropped. `kc-autopilot` 0.2.2's QA persona preloads both, and `kc-gates` 3.1.3's `kc-ready-for-review` runs both for a change a person sees.
- `kc-gates` 3.1.2: a repo can ask for its hand-off checklist before any PR opens, drafts included. With `drafts: true` in `.claude/hand-off-checklist.md`'s front matter, `guard-hand-off.sh` blocks a draft `gh pr create` until its head commit has a receipt; `ready-receipt.sh write <sha> --checklist` records that the checklist alone was walked. The checklist is read at the head commit, from the local clone or GitHub. The full `kc-ready-for-review` pass still guards marking it ready. The kit's own checklist opts in, its `CLAUDE.md` says how to write a lesson before drafting it (the class of mistake and two or three other cases first, suggested wording only a starting point, the checklist graded before the first commit), and a new box checks the PR description names the class. It comes from lessons that went out as draft PRs narrower than the kit's rules allow, which the checklist would have caught if it had run before the draft.
- `kc-verify` 2.0.2: kc-ui gains a usability walk: nobody should have to learn the product to use it. A new hard rule, and in Step 3b, each changed screen is walked toward its goal from each entry point as someone new to the product would, once the page has finished loading. Every place that makes a person stop and work something out is a finding even when everything works as built: an action that lands away from what it names, a screen with no clear next step, a control nobody would find, a step that needs something from another screen, an error with no way forward, a dead end. Familiar flows keep their familiar order, per simplicity §P17. It comes from a "Choose a plan" link that opened its page at the top, with the plans out of sight. Has a gate box.
- `kc-conventions` 2.0.2: simplicity §P17, don't reinvent the wheel for a flow people already know. Sign-up, sign-in, password reset, checkout, account settings and navigation follow the order and behavior people bring from other products, as closely as the product allows, and a shortcut that saves a step by changing that order is not taken. A departure is the developer's product decision, and a flow that copies one the codebase already has is raised, not taken as precedent. Example: a password reset asks for the email, emails a code, then takes the code and the new password. It comes from a reset form that asked for the new password before sending the code and confused the first person who used it. Has a gate box.
- `kc-gates` 3.1.1: `kc-post-review` bans emoji anywhere in a comment or reply, not only as an opener or a stock close.
- `kc-gates` 3.1.0: `kc-ready-for-review`, the one review-and-QA pass on your own PR before a person reviews it. It runs `kc-code-review`, the repo's hand-off checklist (`.claude/hand-off-checklist.md`) and QA, fixes what they find, re-reviews once, and hands what is still open to the user: two rounds at most, nothing per commit or push. It ends in a receipt (`scripts/ready-receipt.sh`) for the head commit, and a new `PreToolUse` hook (`scripts/guard-hand-off.sh`) blocks `gh pr ready`, a ready `gh pr create`, `gh pr edit --add-reviewer` and `gh api` reviewer requests until that commit has one; `KC_READY_SKIP=1` passes when the user says to skip. A `SessionStart` hook (`scripts/session-start.sh`) reminds every session, in every project where the plugin is installed, to run the pass before a hand-off, so the habit needs no per-project setup and no edit to a global instructions file. For the kit's maintainer only (the GitHub user signed in to `gh` owns the repo the copy came from), it adds a second line: feedback worth keeping becomes a generalized kit lesson, shipped as a PR that is merged once its checks pass. The kit's own `.claude/hand-off-checklist.md` checks each lesson PR for generality and for anything naming where the lesson came from. After review, each reviewer comment is sorted as covered (a rule said it, so the check that missed it gets fixed) or new (a new rule). `kc-code-review`'s self-review trigger now points at this pass. The two guards share their payload parsing in `scripts/lib/hook-input.sh`.
- CI fails a pull request that changes a plugin without raising its `plugin.json` version (`scripts/check-version-bumps.sh`). Installed plugins update only when their version goes up, so an unbumped change never reaches anyone: §B14, the gate-kind question, kc-ui's walkthroughs and the shipper's merge order were merged without a bump. `kc-conventions` 2.0.1, `kc-verify` 2.0.1 and `kc-autopilot` 0.2.1 release them.
- `kc-conventions` correctness §B14: a guard that refuses a delete counts only the related records the delete would harm (completed payments, live work), not abandoned, expired, failed or archived ones, and its message says what blocks it and what to do instead. It comes from a storefront that one abandoned checkout locked against deletion. Has a gate box.
- `kc-conventions` working agreement: ask which kind of gate a change goes behind (a paid entitlement, a developers-only flag, a flag support switches from an admin page) and at what level, when the codebase has more than one. It comes from two rollouts built as the wrong kind and rebuilt.
- `kc-instructions` 3.1.0: the audit says what on-demand loading needs. A session started above the repo loads none of the repo's instructions until a file there is opened, and a file read through the shell triggers nothing, so a rule meant to shape a plan never arrives. New box §A16: plan-shaping instructions load at launch, at user scope or from a SessionStart hook, and agents read code with the Read tool. It comes from a session that planned in a workspace folder, read the code with shell commands, and proposed a design the project's path-scoped rules forbid.

### Changed

- Every plugin and skill is renamed with a `kc-` prefix, so none collides with other public plugins and skills, and no plugin shares a name with one of its skills. Plugins: `conventions` is `kc-conventions` (2.0.0), `code-review` is `kc-gates` (3.0.0), `testing` is `kc-verify` (2.0.0), `instructions` is `kc-instructions` (3.0.0), `autopilot` is `kc-autopilot` (0.2.0), `usage-band` is `kc-usage-band` (2.0.0), `image-preview` is `kc-image-preview` (2.0.0). Skills: every conventions topic is `kc-<topic>` (`kc-conventions:kc-naming`), the review skill is `kc-gates:kc-code-review` and the posting skill `kc-gates:kc-post-review`, the verify skills are `kc-verify:kc-ui` and `kc-verify:kc-e2e`, and `kc-autopilot:kc-init`, `kc-autopilot:kc-run`, `kc-instructions:kc-audit`. Agents keep their names under the new plugin (`kc-gates:naming-gate`). The rules a project installs are now `.claude/rules/kc-<topic>.md`; run `/kc-conventions:kc-init` again and delete the old unprefixed copies. Exported skills for other tools are named `<plugin>-<skill>` (`kc-gates-code-review`). Already installed? Reinstall under the new names:

  ```
  claude plugin uninstall conventions@kc-claude-kit code-review@kc-claude-kit testing@kc-claude-kit instructions@kc-claude-kit autopilot@kc-claude-kit usage-band@kc-claude-kit image-preview@kc-claude-kit
  claude plugin install kc-conventions@kc-claude-kit kc-gates@kc-claude-kit kc-verify@kc-claude-kit
  ```

- `claude-md` is renamed `instructions` (2.0.0), and its skill `claude-md:audit` is now `instructions:audit`. Claude Code now reserves plugin names that start with `claude-`, so `claude plugin validate --strict` rejected the old name and failed CI. Already installed? Swap it:

  ```
  claude plugin uninstall claude-md@kc-claude-kit
  claude plugin install instructions@kc-claude-kit
  ```

- `conventions` 1.2.0: "twice is the threshold" is gone from simplicity §P1 and naming §N3. DRY is about knowledge, so a plain expression with two callers stays inline (§P11), and a repeated domain check becomes a named `isX` at three copies, with a single enum comparison exempt (§N3). Clarity §C12 says the same.
- `code-review` 2.2.0: a self-review runs the gate fan-out only when the user asks, or once before opening a PR for a big change, never after each fix.
- `conventions` 1.2.0: to stay under the 500-line cap, clarity's ternary detail, structure's export detail and react's data-fetching and forms detail moved to `skills/<topic>/references/`. Gates now read those files.

### Added

- `kc-verify` kc-ui Step 6b: before review, the ticket's description gets a How to test section (PR links, setup, numbered cases, expected results) with the walkthrough embedded. The walkthrough is a short MP4 (a GIF can't be paused): it opens with the setup, captions each case with its state and expected result, and boxes and labels what to look at. It is embedded as a block player, not an inline file chip, and seen playing on the ticket before review.
- `kc-verify` kc-ui Step 6b: the walkthrough stays sharp. Frames are captured at 2x in a headless browser with captions and boxes drawn into the page, never from an agent tool's downscaled screenshot, and the video is encoded at the frames' own size and checked at 100%.
- `kc-verify` kc-ui Step 6b: the walkthrough is shaped like the screen people use: 16:9 for a product used on laptops, portrait only for a phone ticket, with each case framed on the part that changes instead of a tall full-page shot.
- `kc-verify` kc-ui Step 2: the app is signed in as a seeded local user without anyone's password, through a credential the local backend mints and the frontend sends only in development mode. Guards: a development-only signing secret, a mint command that refuses other environments, a compile-time development check, and a build that fails when the variable is set for production. The user signs in only where no such path exists yet, and it is proposed. Has a gate box.
- `kc-verify` kc-ui Step 6b: the How to test setup, on the ticket and the pull request, is written for the team's usual local environment, never the ports, worktrees or server entries of your own session. Has a gate box.
- `kc-verify` kc-ui Step 6: a QA pass on shipped work ends at the report. No code changes until the findings are triaged with the user (bug or question; hotfix or ticket; what introduced each), and a remark about one finding is not a go-ahead to build it. Has a gate box. It comes from a staging pass where a fix was started from one comment while the other findings were still unsorted.
- `kc-autopilot` shipper: a PR description holds only what a reviewer or deployer acts on, read in a minute, with no per-area breakdown or "why it's safe" essay. A PR in a stack or a cross-repo pair carries the merge order as one numbered list of every PR, introduced by "Merge these PRs in this order." and the same in each, this PR in bold and after-deploy tasks inline, never "deploy X first", and names what breaks between two steps. It comes from a five-PR stack whose descriptions ran to 800 words and whose "deploy the frontend PR first" read either way.
- `kc-conventions` and `kc-gates`: question the approach before the lines. The working agreement gains a section: before writing code or reviewing it, ask whether this is the best and simplest way to get the result, assume a simpler one exists, sketch at least one other shape, and only then go line by line. Simplicity §P16 grades the shape of the whole change: two mechanisms for one job, a later pass recomputing what an earlier step knew, or a layer an existing one could carry fails when another way is materially simpler, and the line findings that shape would delete go under it. `kc-code-review` gains a hard rule and scope box §G5 (audited by the verification gate's §V7), and its report opens with an **Approach:** line. It comes from a review that listed fifteen correct line findings against a change whose simpler design would have deleted most of that code.
