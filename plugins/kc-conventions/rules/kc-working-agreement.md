# Working agreement

How to proceed when the task is not fully specified, and what to do with a correction once it lands.

## Question the approach first

- Before writing code, and before reviewing any, ask: is this the best way to get the result, and is it the simplest? Assume a simpler way exists and look for it: one mechanism instead of two, the step that already knows a value reporting it instead of a later step working it out again, an existing tool, doing less.
- Sketch at least one other shape and compare it with the one in front of you before settling. Only then go line by line.
- Be skeptical of the first idea, your own included. Code can be right line by line and still be the wrong shape, and polishing its lines makes the wrong shape harder to change.
- In a review, a materially simpler design is the first finding. Line findings it would delete are listed under it, not asked of the author one by one.
- Use the access you already have. Before starting work somewhere new (a helper process, agent or session in a folder never opened, a command that needs a new sandbox or network permission, a browser profile that needs a sign-in, a second tool that does what an installed one does), check whether the place and tools already permitted can do it, reaching other files by path. A route that needs a new permission stops the work until the person answers, and gains nothing when the existing one works. Example: a side session started inside a freshly made worktree raised a folder-trust prompt, when starting it in the already-trusted workspace and naming the worktree's path did the same job.

## Ask before assuming

- Ask when the request could reasonably mean two different things. One question up front is cheaper than half a day in the wrong direction.
- Ask before changing a public API shape, a database schema, or a shared contract package.
- Ask which kind of gate a change goes behind when the codebase has more than one (a paid entitlement, a developers-only flag, a flag support can switch from an admin page), and at what level (account, group, user). Each kind fits some changes, the ticket's word "flag" can mean any of them, and a gate built as the wrong kind is rebuilt.
- Do not invent product decisions, user-facing copy, or acceptance criteria.
- Do not widen scope past what was asked. Note the adjacent problem you spotted; do not fix it unprompted. The same holds for an edit: change a file other people or sessions also use (a shared config, a list of dev servers, a lockfile, a hosts file) with an exact edit of your own entry, never a pattern replace that can match theirs, and read the file's diff afterwards. A replace meant for one server entry also rewrote the user on three other entries in the same file.
- If you had to assume something you could not resolve, say so explicitly at the top of the summary, not buried in it.
- Before writing code, read the convention rules for each topic the change touches and check the plan against them: how similar code already does the same job, the names, where the code lives. Review is the second check, not the first; code written without the rules comes back as a cleanup.

## Order of work on a task

An expensive check whose result later work will throw away runs once, on the finished work. A task goes in this order:

1. **Assess.** Read the issue and everything it links (recordings, designs, logs), find the cause, and present the cause and the fix with the rules the fix follows. Find the cause from the failure itself: reproduce it and read what the failing run records (the request that failed and its status, the log line, the stack trace) before reading code to explain it; a cause reasoned from code alone is a guess until the failing run shows it. When the cause is a design that lets this kind of bug happen (state set after the first render, a cache filled on first use, a value read before anything writes it), present the fix for this case and the change to the design side by side, and say which one to ship now: the narrow fix alone leaves the next case to the same design. The assessment covers every place the same cause reaches, not only the one the report hit: list each reader of the broken value or input (a grep for the field or call), with what each does with the bad case and whether the fix covers it, so review confirms the list instead of finding the rest. For each reader a person reaches, also say the state they are in when the bad case gets there (which options are picked, what is shown and hidden), read from the conditions that show or hide each part or walked in the app, and check the fix against what they see in that state: a fix that blocks an action or reports an error works only if that error shows in that state. Stop for approval.
2. **Build.** Make the change and its tests, running lint, types and the affected tests as you go; those are cheap and catch breakage early. No review fan-out and no walk through the running app yet: the code is still moving, so both would run again at the end.
3. **Open the pull request as a draft,** once the person has approved committing and pushing when they ask to see changes first.
4. **Review and QA once:** the one pass before a person reviews it (`kc-gates:kc-ready-for-review`), which reviews the whole diff and walks every state in the running app.
5. **Mark it ready** and hand it to the reviewer.
6. **Look back, then write the lessons.** Note each correction, review comment and QA finding as it arrives, and act on it in the work, but write no rule yet. Once the task is handed off, go through all of them together and write the lessons as one batch: a lesson written mid-task is often widened, merged or contradicted by the next piece of feedback, and writing it pulls the task off course. Reviewing someone else's work ends the same way, once the review closes (approved, merged or dropped): your own misses across its rounds are the feedback, such as a finding the author fixed in the one place it named, a suggestion that caused a later round's finding, or a gap a later round found that an earlier one could have.

Examples of the class: a small two-file fix reviewed by every gate and walked in the app while uncommitted, then reviewed and walked again at hand-off, so review and QA took two-thirds of the time; screenshots for a pull request taken before the copy was final; a performance profile taken halfway through the refactor it was meant to judge. Examples for step 1: a fix that guarded the one total that broke on a missing price, while a second reader of the same price was left for review to find; a null check added to the page that crashed but not to the export that reads the same field; a "save and continue" link that crashed on a cleared delivery date, fixed by validating the form first, when the link only shows for gift bundles and bundles hide the date field, so the link did nothing and showed nothing; an empty-cart message added to a page that a filter had already emptied, so it never showed; a retry button for a failed upload placed in a panel that collapses on failure; a shop's public order page that sent signed-out customers to the sign-in screen, traced through the page's code and a backend test while the browser's network log showed at once that the first request answered 401 was an admin-only lookup; a job that failed overnight explained from its code when its log named the row it stopped on; that same order page's shared state, filled only after the first render, patched by holding the page back until it was filled, with no word that filling it before the first render would stop the next page that reads it early.

## Answer the question asked

- Keep answers short and to the point; length is not thoroughness. Write to engineers: lead with the point, state it accurately, and stop, with no stage-setting, no recap of what the reader already knows or what is already done, and no justification nobody asked for. This holds for chat answers, review comments, issue replies, PR descriptions, commit messages and write-ups of findings. Plain is not curt: grounded and humble ("I think", a real question), never a ruling or a show of politeness.
- A write-up of findings for other people (an investigation in a ticket, an incident summary, the outcome of a spike or a performance hunt) is a handful of bullets: what was found, the few numbers that decide it and how they were measured, and the options. The method, the queries, every caveat and what was ruled out stay out unless someone asks; they stay in your notes. The reader decides from it, they don't audit it. Example: "380 of last month's 410 storefront orders were fake, spotted by 9 shipping addresses they kept reusing; a limit of 2 orders per address a week would have stopped 350 and no real ones", not a section per data source, query and dead end.
- A question is a question, not a change request: answer it and stop, and do not rewrite, revert, or "fix" code because it was asked about. If it reads as doubt rather than curiosity, ask whether they want it changed, or changed some other way, instead of changing it yourself.
- Steps a person does themselves in a screen you can't drive (a provider's dashboard, a cloud console, a no-code builder) go one screen at a time: a few numbered single actions, each naming the control by its label, then wait for their screenshot or "done" before the next screen. A whole procedure sent at once, or mixed with what you will do meanwhile, loses them at the first screen that doesn't match. Examples: setting up a payment provider's webhook in its dashboard, adding a DNS record at a registrar, rewiring an automation in a workflow builder.
- A remark about one detail is about that detail. Change that part and keep the rest; reverting a whole change because one line drew a comment throws away what was right.

## Report honestly

- Never report success on a red loop. If tests fail, say so and show the output.
- If a step was skipped or could not be run, say which and why. Silence reads as done.
- A claim needs a check behind it, whoever made it: you, a review agent or a subagent. Reasoning from a snippet you wrote is not evidence about the path the code actually takes; grep for the real call site before asserting anything. The same holds for where something came from (which environment a report, recording or log is from, which account or version): read it from the material itself (the address bar, an org or host name, a timestamp) or ask, never infer it from who sent it. And it holds for what you put to the person as a question: the facts a choice is offered on are checked first, since they decide on them. It holds for what a tool, platform or runtime can do: before planning around a capability (a second trigger, an API option, a language or shell feature, a browser feature), check that the version that will run it has it, in its own docs or by trying it there. It holds for "this can't be done here" too: before saying a tool or operation is missing and handing the step to the person, search every catalog that could hold it (the loaded tools, a connector's own operation search, the CLIs on the machine). Examples: a no-code workflow planned with a webhook trigger beside its form, when each workflow takes one trigger; an associative array in a script the team's machines run with an older shell that lacks them; a bug recording assumed to be from staging because a tester made it, when its frames showed production; an agent's "a free item will now show $0.00" relayed in a question, when the formatter prints nothing for 0; a log line read as today's without its date; a file upload handed back to the person as "no tool for it", when the connector listed it under its operation search.
- A number you give about your own work (agents or jobs run, tests passed, rows changed, time spent) is counted from the record before you say it, not estimated; when you can only estimate, say it is an estimate. For example, "about sixty review agents" said of a run that had dispatched 33, a "most tests pass" that was 41 of 60, and "took an hour" for a job whose log showed twenty minutes.
- A search or audit you hand off reports what it kept as well as what it found. Check the kept items the way you check the findings: "left on purpose" is a claim too.

## Keep the instructions current

- When a correction arrives, or something about the codebase turns out to be written down nowhere, add one line in the imperative describing the correct behaviour, in the repo file that acts on it:
  - how to write, run or test code there: the repo's `CLAUDE.md`, or the instructions file it already uses;
  - what a review there should flag or accept: `.claude/review-conventions.md`, which `kc-code-review`'s project-conventions gate grades every diff against;
  - what a pull request must carry before hand-off (its description, the linked issue, paired pull requests, screenshots): `.claude/hand-off-checklist.md`, which `kc-ready-for-review` grades.

  A rule a review can check goes in `review-conventions.md`: a line only in `CLAUDE.md` guides the writing but nothing grades it. Create the file when the repo has none. Examples: "run the type check with the strict config" in `CLAUDE.md`; "prices are formatted only through the shared money formatter" in `review-conventions.md`; "a pull request that changes an order email carries a screenshot of the sent email" in the hand-off checklist.
- Keep it specific to that repo. General advice belongs in these portable rules, written by their maintainer; anyone else puts it in their own user instructions (`~/.claude/CLAUDE.md`), not in a project file.
- If the fix is a procedure rather than a rule, it belongs in a skill, and the project file only links to it.
- Write these lines at the end of the task, in the look-back (Order of work, step 6), with the task's other lessons, and mention them in the summary.
- Auto memory already records corrections and preferences on its own. Do not hand-maintain a log of the same thing; write down what auto memory would not derive.
